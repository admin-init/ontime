## 0. 一页结论

**一个 FastAPI 服务 + 一个 SQLite 文件 + 一个 React 前端**（构建产物由 FastAPI 托管，演示只有一个地址）。四种输入统一成同一种 `Source`，再用「带原文引用的字段断言（Claim）」表达事实。事件卡只是这些断言的一个视图。

三个决定性的设计选择（与选型无关，是这个产品的地基）：

1. **Claim 是唯一事实来源。** `Event.title`、`Task.due_at` 这类字段是从 Claim 派生出来的"当前视图"。任何新信息都不 UPDATE 旧值，只追加 Claim 与 Change。→ 字段级溯源、冲突可见、静默覆盖，全部由数据的形状保证，不依赖 UI 自觉。
2. **每个字段值必须携带原文片段，写入前用确定性代码校验片段确实存在于来源文本。** → 一套机制同时得到三件事：防幻觉、点击定位高亮、**变更检测**（重新抓取后旧片段消失 = 该字段过期，自动生成变更提案）。不需要单独写 diff 算法。
3. **模型只做语义，不做判断。** 日期换算、状态流转、合并守卫、高影响规则门槛、提醒调度，全部是普通 Python 代码。模型输出必须可校验、可驳回。

**为什么这次 FastAPI 更合适**：本项目七成工作量在"文本处理"而不是"页面渲染"——PDF/DOCX 附件、中文正文抽取（trafilatura）、OCR（PaddleOCR）、邮件解析（`email` / `imap-tools`）、日历（`icalendar`）都在 Python 侧最成熟；Pydantic v2 天然就是"模型输出契约"的载体，和校验闸门是同一套类型；OpenAPI 自动生成前端 TypeScript 类型，前后端契约不会漂移。代价是两个进程、表单样板代码更多，用 TanStack Query + 生成的 client 抵消。

预计 **12 人日**走完全部里程碑；紧的话有 **7 天裁剪版**（见 §11）。

## 1. 原型边界

### 1.1 必须打通的闭环（10 分钟能演完）

| # | 动作 | 用户看到什么 |
|---|---|---|
| 1 | 官网栏目抓到「创作工作坊」通知 | 收件箱出现候选事件，活动时间与报名截止是**两个字段** |
| 2 | 导入一封补充材料要求的邮件 | 系统提出合并建议，合并后事件下多出一条材料任务，两个字段各自带来源 |
| 3 | 粘贴一张聊天截图（地点有变） | 识别出「地点变更」提案，标出截图来源，**不自动覆盖** |
| 4 | 对某条逾期后果点「联网核实」 | 找到官网原文 → 显示原文片段；找不到 → 明确显示「未确认」，不编规则 |
| 5 | 确认后导出 `.ics` | 行动台出现倒计时，事件详情能看到完整时间线、字段出处、变更历史 |

判断标准：**五个场景围绕同一个事件发生**，而不是五个互不相通的 Demo 页面。

### 1.2 首版明确不做

- 多用户、注册登录、权限体系（单 Profile 本地使用；模型里预留但不上）
- 全国高校通用爬虫（只做 1 个学校的 1–2 个栏目，适配器可插拔）
- 登录态教务系统、聊天软件自动读取、系统级截屏
- 自动合并、自动发邮件、代报名、代交材料
- 自动裁定高影响规则（只做「找到明确依据」或「未确认」两态）
- 中文分词与语义检索（几千条以内用 `LIKE` / FTS5 trigram 足够）

### 2.3 交付形态

- **开发**：两个终端。`uv run uvicorn app.main:app --reload`（:8000）+ `npm run dev`（:5173，Vite 代理 `/api` → :8000）。
- **演示/交付**：`npm run build` → 产物输出到 `backend/app/static/`，FastAPI `StaticFiles` 托管，**只有一个地址、没有 CORS**。一条 `scripts/demo.ps1` 起服务并打开浏览器。

## 3. 数据模型：以 Claim 为中心

### 3.1 表一览

| 表 | 作用 | 关键点 |
|---|---|---|
| `profile` | 学校、学院、年级、适用身份 | 单行；决定"这条规则适不适用我" |
| `watch_target` | 官网栏目 / 邮箱的抓取配置 | 启停、cron、最近一次错误 |
| `source` | **一条来源记录**（网页/邮件/截图/文本/链接） | 归一化后的 `text` 是 Claim 校验的唯一基准 |
| `pipeline_run` | 每次解析的阶段、耗时、模型原始输出 | 排查与回放的证据 |
| `event` | 活动（有开始/结束） | `start_precision`：只知道日期还是准确到分钟 |
| `task` | 要做的动作（报名、交材料） | `due_at` 与 `event.start_at` **永不共用字段** |
| `rule` | 规则条款（资格、格式、逾期后果） | `impact=high` 要过门槛才显示 |
| `claim` | **字段级断言**：某字段的某值，出自哪条 Source 的哪句原文 | 全系统的原子事实 |
| `change` | 字段变更提案 | 待确认 / 已确认 / 已拒绝；可撤销 |
| `merge_candidate` | 两条事件是否同一件事 | 先确定性守卫，再模型复核，最终用户点 |
| `job` | 后台任务队列 | 轮询、重试、幂等键 |
| `reminder` | 提醒调度 | 导出 ics / 站内 |

`claim` 用 `entity_type + entity_id` 指向 Event/Task/Rule，不做数据库外键（多态关联的常规取舍），由服务层保证一致性。

完整定义见 `backend/app/models.py`（随本方案提交，`uv run python -c "import app.models"` 可验证）。

### 3.2 Claim 的状态机

```
unverified ──校验通过──> supported ──用户点确认──> user_confirmed
     │                      │
     │                      ├──同一字段出现不同值──> conflict
     └──校验不通过──> rejected      （由用户裁决，保留全部候选）

supported ──重新抓取后原文片段消失──> stale ──> 生成 Change 提案

缺少日期锚点的相对时间 ──> needs_anchor（value 为空，生成待确认项）
```

- `conflict` 不是布尔值，而是"同一 `(entity_type, entity_id, field)` 下存在 ≥2 条 `supported` 且值不同的 Claim"。
- 展示规则：有 `user_confirmed` 用它；否则只有一条 `supported` 用它；否则取最新 `supported` 并挂冲突角标；否则显示「待确认」。
- **代码里禁止** `event.start_at = x` 这类直接赋语义字段的写法。所有写入走 `services/claims.py` 的 `append_claim()`，由它决定是否刷新视图。加一条 CI 检查：`app/services` 之外禁止给 `Event/Task/Rule` 的语义字段赋值。

### 3.3 三条不能违反的约束

1. **任何进入 `event/task/rule` 的字段，都必须有一条对应 Claim 指向具体 Source。** 用户手填的值 `origin=user`，`source_id` 指向一条 `kind=text` 的自建来源（内容即用户输入），因此也永远可溯源。
2. **删除字段 = 新增一条 `value=null` 的 Claim，不物理删除。**
3. **高影响规则（`impact=high`）只有 `status in (supported, user_confirmed)` 才能渲染。** 其余渲染「未确认，请咨询负责部门」。纯代码判断，不交给模型。

关于用户删除：删除来源是用户的权利。删除 `source` 时级联删除其 Claim（该字段回到「待确认」），但 `change` 表保留 old/new 与原因作为操作留痕；UI 必须提示"该字段将回到待确认"。

## 4. 解析契约（防幻觉的核心）

### 4.1 输入信封 Envelope

所有入口先归一到同一个结构再进管线：

```python
class Envelope(BaseModel):
    kind: Literal["text", "link", "screenshot", "mail", "web"]
    raw_text: str                      # 截图先由 OCR/VLM 转成文字
    image_path: str | None = None      # 原图本地路径，不外发（除非启用 VLM）
    url: str | None = None
    title: str | None = None
    org_hint: str | None = None
```

**归一化**（`services/normalize.py`）：全角转半角、去零宽字符、压缩空白、统一引号、去页眉页脚。`source.text` 存归一化结果，Claim 校验与高亮都以它为准。

### 4.3 校验闸门（`app/services/pipeline/gate.py`）

```python
for path, field in flatten(result):
    if field.value is None:
        continue
    quote = normalize(field.quote or "")
    if not quote or quote not in source.text:
        drop(field)                                  # 丢弃臆造字段
        ask(path, "原文中未找到依据")
        continue
    field.quote_start = source.text.index(quote)
    field.quote_end = field.quote_start + len(quote)
    field.precision = infer_precision(quote, field.value)   # 原文只有日期就别保留时分
    field.status = "supported"
```

成本几乎为 0，但能把"流畅的胡说"挡在入库之前。**这是本项目最值得写进答辩 PPT 的一页。**

### 4.4 日期与时间

- 全部存 UTC；展示按 `profile.timezone`（默认 `Asia/Shanghai`）。
- `precision ∈ {date, datetime, range}`；"11月10日前" 解析为 `2026-11-10T23:59:59+08:00` + `precision=date`，UI 显示"11月10日前"，不显示"23:59 截止"。
- **相对日期必须有锚点**：`明天/后天/下周三` 只有在来源自带 `published_at`（网页发布时间、邮件 `Date` 头、聊天可见日期）或用户手动指定时才换算；否则字段置 `needs_anchor`，生成待确认项。**绝不使用上传时间或当前时间补齐。**
- 无年份的"11月10日"：以锚点年份为基准；若换算结果早于锚点 180 天以上，视为次年，并在 UI 标注推断依据。

### 4.5 事件 / 任务 / 规则三分

- 报名截止、材料提交、签字 → `task.due_at`；活动开始、讲座时间 → `event.start_at`。
- 结构补检：若 `event.start_at` 存在且原文出现 `报名|截止|提交|前将`，但 `tasks` 为空 → 生成 `open_question`，不静默通过。
- 高影响关键词表：`扣分|取消资格|不予|逾期|处分|罚款|不退|视为放弃`。命中则 `impact=high`，走 §3.3 第 3 条门槛。

## 5. 五条流水线

统一入口 `POST /api/ingest` → 写 `source` + `job` → worker 执行 `ingest → extract → gate → link`。

### 5.1 文本 / 链接收录（最短路径，先做）

输入框或链接 → `httpx` + trafilatura 取正文 → 归一化 → 模型抽取 → 闸门 → 生成候选事件/任务 + Claim → 收件箱。
失败态：抓不到正文 → 保留 URL，提示"粘贴正文"。

### 5.2 截图

上传 / 粘贴（前端剪贴板 `ClipboardEvent` 取图）→ Pillow 清 EXIF、按需裁剪 → 存 `storage/`（本地，不入库不入 git）→ **OCR 提供方（见 §10）** → 文字 + 布局提示 → 后续同 5.1。
额外处理：
- 从可见文字里找聊天日期/发送人，作为 `message_date` 锚点；读不出就 `needs_anchor`。
- 原文展示用识别文本高亮，原图作为附件预览。

### 5.3 官网抓取 + 变更检测

`watch_target` → APScheduler cron（或手动"立即同步"按钮）→ Playwright 打开栏目页 → 取文章列表（选择器 + 兜底：标题相似度）→ 新文章入库。
**变更检测复用 Claim 闸门**：对已有 Source 重新抓取正文，逐条 Claim 检查 `quote in source.text`：
- 仍在 → 无变化（顺带刷新 `quote_start`）
- 消失 → 该 Claim 置 `stale` → 对新正文跑抽取 → 同字段出现不同值则生成 `Change`（待用户确认）

"官网改了截止时间"因此不需要单独的 diff 算法。

### 5.4 邮件

- **导入（默认，演示用）**：`.eml` / `.mbox` → 标准库 `email` 解析 → `subject/from/date/text/html/attachments` → PDF 用 pypdf、图片走 5.2 → 抽取。约 60 行，直接做完。
- **IMAP 只读（已实现，演示不启用）**：`imap-tools` 连接 → `SINCE`/`SUBJECT` 检索 → 只取需要的邮件；凭证只来自本地 `.env`，**不进数据库、不进仓库、不上传**。
- 两个实现挂在同一个 `MailSource` 协议下，UI 的入口与配置表单完全一致，只是 IMAP 那侧标"需要自备账号"，演示环境不连接。

### 5.5 联网核实

```
query = f"{profile.school} {profile.college or ''} {event.title} {意图词} site:{school_domain}"
意图词 ∈ {通知, 报名, 材料, 截止, 实施办法}
```

1. 搜索拿 3–5 条候选 → 抓正文 → 用**同一个抽取器**抽字段。
2. 逐字段比对：候选值通过闸门 → 新 Claim（`origin=rule`），UI 显示"官网支持 / 与现有值冲突"。
3. 适用性复核：模型输入 `{profile, 事件, 候选来源}`，输出 `{applies: yes|no|unknown, reason, evidence_quote}`。`unknown` → 信息不足。
4. **身份线索不足时先问**（学校/学院/年级），不默认采用第一条结果。

耗时 8–20s：前端轮询 `job` 状态，展示"正在核实…（已找到 3 条候选）"，可离开页面。

## 6. 合并：先守卫，再模型，最后用户

```python
def merge_guard(a: Event, b: Event) -> GuardResult:
    term_a, term_b = term_key(a), term_key(b)      # 2026春 / 第3届 / 2026级
    if term_a and term_b and term_a != term_b:
        return GuardResult(score=0, reasons=["届次/学期不同"])

    score, reasons = 0, []
    if title_similarity(a.title, b.title) >= 0.6: score += 1
    if a.org and a.org == b.org:                  score += 1; reasons.append("组织方一致")
    if a.start_at and b.start_at and days_between(a.start_at, b.start_at) <= 3: score += 1
    if same_source_family(a, b):                  score += 1     # 同域名 / 同一邮件线程
    return GuardResult(score=score, reasons=reasons)
```

`score >= 2` 才进入候选，再由模型判断"是否同一件事、差异字段有哪些"，输出理由。**原型阶段一律不自动合并**，`merge_candidate` 出现在收件箱，用户点「合并 / 不是同一件事」。
合并实现：`event.merged_into_id` + Claim 改指向（不复制值），因此**可撤销**——撤销即清空 `merged_into_id`，原事件与 Claim 全在。
显式反例测试：同名不同届次 → `score=0`；同名同日不同学院 → 不合并。

## 10. OCR 双实现与隐私分级

### 10.1 一个接口，两个实现

```python
class OcrProvider(Protocol):
    name: str
    async def read(self, image: bytes) -> OcrResult: ...   # text + layout hints + confidence
```

| 实现 | 依赖 | 速度 | 中文聊天截图 | 图片是否离开本机 |
|---|---|---|---|---|
| `VlmOcr`（默认） | 视觉模型 API | 3–8s | 好，能理解气泡与上下文 | **是** |
| `PaddleOcr` | `paddleocr` + `paddlepaddle`（`uv sync --extra ocr`，约数百 MB） | 本地 1–3s，首次加载慢 | 好，纯文字识别 | 否 |

切换：`OCR_PROVIDER=vlm|paddle`。截图可选"用于脱敏的裁剪框"，两个实现都走同一个入口。

### 10.2 必须讲清楚的隐私局限

这是用户最容易误解的地方，也是答辩时最容易被追问的地方——**本地 OCR ≠ 数据不出本机**：

| 模式 | 原图出本机 | 识别文本出本机 | 说明 |
|---|---|---|---|
| 默认：视觉模型直读 | **是** | 是 | 图片里可能有他人姓名、头像、群名、上下文 |
| 本地 OCR + 云端文本模型 | 否 | 是 | 只发文字，但聊天原文仍会被发送 |
| 本地 OCR + 本地模型（Ollama / vLLM） | 否 | 否 | 需自备算力，效果下降；接口已兼容 OpenAI 协议，改 `LLM_BASE_URL` 即可 |

落地要求：

- 设置页把上表原样展示，并标注当前生效模式。
- 截图上传前提示"图片可能包含他人姓名/头像，建议裁剪"，提供一键删除原图。
- `source.image_path` 只存本地路径；`storage/` 在 `.gitignore` 里；演示素材统一脱敏。
- 外部网页/邮件/截图里的文字一律视为数据，**不进系统提示、不触发工具调用**（抽取器只返回 JSON，没有工具权限）。

## 附录 A：为什么不用向量库

原型的数据量是"几十到几百条通知"。合并候选用确定性特征（标题 trigram + 组织 + 时间邻近 + 同源域）召回，召回率足够且**可解释**——评委问"为什么合并这两条"时，能指着四条理由回答。向量检索留到有上千条历史数据、需要"找相似往年通知"时再上。

## 附录 B：为什么不上 Celery / Redis

原型的最优解是"一个进程能跑起来"。`Job` 表 + 进程内轮询在几十条任务量级完全够用，失败可见、可重试、可演示；引入 Celery 只会多两个要启动的东西和一类排障场景。技术复杂度留给真正难的部分：**证据模型**。
