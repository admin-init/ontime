状态：可开工。未拍板项集中在第 11 节，其余按本方案执行。

## 0. 一页结论

**一个 Next.js 应用 + 一个 SQLite 文件 + 一个后台 worker**，把「截图 / 文本 / 官网 / 邮件」四种输入统一成同一种 `Source`，再用「带原文引用的字段断言（Claim）」表达事实。事件卡只是这些断言的一个视图。

三个决定性的设计选择：

1. **Claim 是唯一事实来源。** `Event.title`、`Task.dueAt` 这类字段是从 Claim 派生出来的"当前视图"。任何新信息都不 UPDATE 旧值，只追加 Claim 与 Change。→ 字段级溯源、冲突可见、静默覆盖，全部由数据的形状保证，不依赖 UI 自觉。
2. **每个字段值必须携带原文片段，写入前用确定性代码校验片段确实存在于来源文本。** → 一套机制同时得到三件事：防幻觉、点击定位高亮、**变更检测**（重新抓取后旧片段消失 = 该字段过期，自动生成变更提案）。
3. **模型只做语义，不做判断。** 日期换算、状态流转、合并守卫、高影响规则门槛、提醒调度，全部是普通 TypeScript 代码。模型输出必须可校验、可驳回。

演示形态：本地 `localhost` 跑完整流程，外部调用全部有**录制/回放层**，现场断网也能演。

**技术栈一句话**：Next.js 15（App Router）+ TypeScript + Tailwind + shadcn/ui，Prisma + SQLite，后台 worker 同进程起一个轮询器，模型走 OpenAI 兼容接口，截图用视觉模型直读，官网用 Playwright 抓单站点，邮件先做 `.eml/.mbox` 导入。

预计 **11 人日**走完全部里程碑；紧的话有 **7 天裁剪版**（见 §9）。

## 1. 原型边界

### 1.1 必须打通的闭环（10 分钟能演完）

| # | 动作 | 用户看到什么 |
|---|---|---|
| 1 | 官网栏目抓到「创作工作坊」通知 | 收件箱出现候选事件，活动时间与报名截止是**两个字段** |
| 2 | 导入一封补充材料要求的邮件 | 系统提出合并建议，合并后事件下多出一条材料任务，两个字段各自带来源 |
| 3 | 粘贴一张聊天截图（地点有变） | 识别出「地点变更」提案，标出截图来源，**不自动覆盖** |
| 4 | 对某条逾期后果点「联网核实」 | 找到官网原文 → 显示原文片段；找不到 → 明确显示「未确认」，不编规则 |
| 5 | 确认后导出 `.ics` | 行动台出现倒计时，事件详情能看到完整时间线、字段出处、变更历史 |

判断标准：**五个场景围绕同一个事件发生**，而不是五个互不相通的 Demo 页面。

### 1.2 首版明确不做

- 多用户、注册登录、权限体系（单 Profile 本地使用；预留 `userId` 字段但不实现）
- 全国高校通用爬虫（只做 1 个学校的 1–2 个栏目，站点适配器可插拔）
- 登录态教务系统、聊天软件自动读取、系统级截屏
- 全邮箱服务商适配（只做标准 IMAP 或文件导入二选一）
- 自动合并、自动发邮件、代报名、代交材料
- 自动裁定高影响规则（只做「找到明确依据」或「未确认」两态）

## 2. 技术选型与理由

| 决策点 | 选择 | 为什么 | 备选（何时换） |
|---|---|---|---|
| 形态 | Web 单页应用，响应式 | 一个地址演示四个入口；手机端用上传/粘贴即可，不做 App | 微信小程序（确认赛事要求后） |
| 框架 | Next.js 15 App Router + TS | 前后端同一进程、同一语言，省掉联调；Server Actions 直接调服务层 | FastAPI + React（若 OCR 必须本地 PaddleOCR） |
| UI | Tailwind + shadcn/ui | 不写样式也能达到可演示的观感；组件可改源码 | Ant Design（企业风，偏重） |
| 数据库 | Prisma + SQLite（本地） | 零部署、演示可打包、`seed` 一条命令重置 | Postgres（上公网时，见下） |
| 后台任务 | DB 里的 `Job` 表 + 进程内轮询 worker | 不引入 Redis/BullMQ；原型阶段并发量极小；`npm run worker` 即可 | BullMQ（多实例时） |
| 模型 | OpenAI 兼容适配层（DeepSeek / Qwen / GPT 可换） | 只依赖 `/chat/completions` + JSON 输出，换供应商改一个环境变量 | — |
| 结构化输出 | 模型返回 JSON → **zod 校验** → **原文片段校验** | 两道闸门，任何一道不过就丢字段并转成待确认项 | — |
| OCR | **视觉模型直读截图**（默认） | 一次调用同时拿到文字与结构，省掉 OCR→解析两段；中文聊天截图效果好 | PaddleOCR 本地 sidecar（成本/隐私要求时，接口不变） |
| 官网抓取 | Playwright（headless chromium）+ `@mozilla/readability` | 能过 JS 渲染；正文抽取成熟；同时存 HTML 快照用于 diff | `fetch` + cheerio（静态站更轻） |
| 邮件 | `.eml / .mbox` 文件导入（v0）+ `mailparser` | 不碰账号密码，零授权风险，演示可控；IMAP 只读作为 v1 | `imapflow` IMAP 只读（有真实账号时） |
| 联网核实 | `SearchProvider` 接口，默认博查/Tavily，`site:` 限定域名 | 可替换；限定校域能显著降噪 | Bing / Serper |
| 提醒 | `.ics` 导出（VEVENT + VALARM）+ 站内倒计时 | 满足"一种提醒方式或日历导出"；不依赖推送资质 | Web Push（VAPID） |
| 测试 | Vitest + fixture 驱动 | §12 的验收条目直接写成测试，评审可现场跑 | — |

**数据库可移植性约定**：SQLite 不支持原生 enum，Prisma 的 Json 类型在 SQLite 上也不稳定。所以全部枚举写成 `String`、全部 JSON 写成 `String`，**在服务层用 zod 收口**。上 Postgres 时只需替换 provider 并把这两类字段换成原生类型，业务代码不动。

## 3. 数据模型：以 Claim 为中心

### 3.1 表一览

| 表 | 作用 | 关键点 |
|---|---|---|
| `Profile` | 学校、学院、年级、适用身份 | 单行；决定"这条规则适不适用我" |
| `WatchTarget` | 官网栏目 / 邮箱的抓取配置 | 启停、cron、最近一次错误 |
| `Source` | **一条来源记录**（网页/邮件/截图/文本/链接） | 归一化后的 `text` 是 Claim 校验的唯一基准 |
| `PipelineRun` | 每次解析的阶段、耗时、模型原始输出 | 排查与回放的证据 |
| `Event` | 活动（有开始/结束） | `startPrecision`：只知道日期还是准确到分钟 |
| `Task` | 要做的动作（报名、交材料） | `dueAt` 与 `Event.startAt` **永不共用字段** |
| `Rule` | 规则条款（资格、格式、逾期后果） | `impact=high` 的要过门槛才显示 |
| `Claim` | **字段级断言**：某字段的某值，出处是哪条 Source 的哪句原文 | 全系统的原子事实 |
| `Change` | 字段变更提案 | 待确认 / 已确认 / 已拒绝；可撤销 |
| `MergeCandidate` | 两条事件是否同一件事 | 先确定性守卫，再模型复核，最终用户点 |
| `Job` | 后台任务队列 | 轮询、重试、幂等键 |
| `Reminder` | 提醒调度 | 导出 ics / 站内 |

`Claim` 用 `entityType + entityId` 指向 Event/Task/Rule，不做数据库外键（多态关联的常规取舍），由服务层保证一致性。

### 3.2 Claim 的状态机

```
unverified ──校验通过──> supported ──用户点确认──> user_confirmed
     │                      │
     │                      ├──同一字段出现不同值──> conflict
     └──校验不通过──> rejected      （由用户裁决，保留全部候选）
                            
supported ──重新抓取后原文片段消失──> stale ──> 生成 Change 提案
```

- `conflict` 不是一个布尔值，而是"同一 `(entityType, entityId, field)` 下存在 ≥2 条 `supported` 且值不同的 Claim"。
- 展示规则：有 `user_confirmed` 用它的值；否则只有一条 `supported` 用它的值；否则取最新 `supported` 并在旁边挂冲突角标；否则显示「待确认」。
- **代码里禁止**：`prisma.event.update({ data: { startAt } })` 这类直接改语义字段的写法。所有写入都走 `appendClaim()`，由它决定是否刷新视图（新增 `lib/claims.ts` 并在 PR 评审时拦截）。

### 3.3 三条不能违反的约束

1. **任何进入 `Event/Task/Rule` 的字段，都必须有一条对应 Claim 指向具体 Source。** 用户手填的值 `origin=user`，`sourceId` 指向一条 `kind=text` 的自建来源（内容为用户输入本身），因此也永远可溯源。
2. **删除字段 = 新增一条 `value=null` 的 Claim，不物理删除。**
3. **高影响规则（`impact=high`）只有 `status in (supported, user_confirmed)` 才能渲染。** 其余情况渲染「未确认，请咨询负责部门」。这是纯代码判断，不交给模型。

完整 schema 见 `prisma/schema.prisma`（随本方案一起提交，`npm i` 后 `prisma validate` 校验）。

## 4. 解析契约（防幻觉的核心）

### 4.1 输入信封 Envelope

所有入口先归一到同一个结构，再进管线：

```ts
type Envelope = {
  kind: 'text' | 'link' | 'screenshot' | 'mail' | 'web'
  rawText: string            // 截图先 OCR/直读得到文字
  imageRef?: string          // 原图路径（不对外发送）
  url?: string
  title?: string
  orgHint?: string
  publishedAt?: string       // 来源自带的发布时间，作为日期锚点
  messageDate?: string       // 邮件的 Date 头
  mailMeta?: { from: string; subject: string; messageId: string }
}
```

**归一化**（`normalizeText`）：全角转半角、去零宽字符、压缩空白、统一引号。`Source.text` 存归一化结果，Claim 校验与高亮都以它为准。

### 4.2 模型输出 JSON（单次调用）

```jsonc
{
  "doc_type": "notice | news | chat | mail | unknown",
  "actionable": true,
  "actionable_reason": "含报名截止与活动时间，需要行动",
  "anchors": [
    { "kind": "published_at", "value": "2026-11-05", "quote": "2026年11月5日" }
  ],
  "events": [{
    "title":    { "value": "创作工作坊", "quote": "创作工作坊" },
    "start_at": { "value": "2026-11-12T14:00:00+08:00", "precision": "datetime", "quote": "11月12日（周四）14:00" },
    "end_at":   { "value": null, "precision": null, "quote": null },
    "location": { "value": "老地方", "quote": "老地方", "needs_clarification": true }
  }],
  "tasks": [{
    "action": "提交报名表",
    "due_at": { "value": "2026-11-10T23:59:00+08:00", "precision": "datetime", "quote": "11月10日前" },
    "materials": [{ "value": "一页项目介绍", "quote": "一页项目介绍" }],
    "submit_channel": { "value": null, "quote": null }
  }],
  "rules": [{
    "text": "逾期不予受理",
    "impact_hint": "high",
    "quote": "逾期不予受理"
  }],
  "open_questions": [
    { "field": "event.location", "question": "截图提到「老地方」，请确认具体地点" }
  ]
}
```

规则：**找不到就 `null`**，不允许推测填空；`quote` 必须是原文连续片段。提示词里给 2 个正例、2 个反例（"据往年安排推测…"属于禁止）。

### 4.3 校验闸门（`lib/pipeline/validate.ts`）

```ts
for (const field of flattenFields(output)) {
  if (field.value == null) continue
  const quote = normalizeText(field.quote ?? '')
  if (!quote || !source.text.includes(quote)) {
    drop(field)                                   // 丢弃臆造字段
    openQuestion(field.path, '原文中未找到依据')
    continue
  }
  field.quoteStart = source.text.indexOf(quote)
  field.quoteEnd = field.quoteStart + quote.length
  // 精度对齐：原文只有日期就别保留时分
  field.precision = inferPrecision(quote, field.value)
  field.status = 'supported'
}
```

调用成本几乎为 0，但能把"流畅的胡说"挡在入库之前。**这是本项目最值得写进答辩 PPT 的一页。**

### 4.4 日期与时间

- 全部时间存 UTC ISO；展示按 `Profile.timezone`（默认 `Asia/Shanghai`）。
- `precision ∈ {date, datetime, range}`；"11月10日前" 解析为 `2026-11-10T23:59:59+08:00` + `precision=date`，UI 显示"11月10日前"而不是"23:59 截止"。
- **相对日期必须有锚点**：`明天/后天/下周三` 只有在来源自带 `publishedAt`（网页发布时间、邮件 Date 头、聊天消息自带日期）或用户手动指定时才换算；否则字段置 `needs_anchor`，生成待确认项。**绝不使用上传时间或当前时间补齐。**
- 无年份的"11月10日"：以锚点年份为基准，若换算结果早于锚点 180 天以上则视为次年，并在 UI 标注推断依据。

### 4.5 事件 / 任务 / 规则三分

- 报名截止、材料提交、签字 → `Task.dueAt`；活动开始、讲座时间 → `Event.startAt`。
- 校验器补一条结构检查：若 `event` 有开始时间且原文出现 `报名|截止|提交|前将`，但 `tasks` 为空 → 生成 `open_question`，不静默通过。
- 规则的高影响关键词表：`扣分|取消资格|不予|逾期|处分|罚款|不退|视为放弃`。命中则 `impact=high`，走 §3.3 第 3 条门槛。

## 5. 五条流水线

统一入口：`POST /api/ingest` → 写 `Source` + `Job` → worker 执行 `ingest → extract → validate → link`。

### 5.1 文本 / 链接收录（最短路径，先做）

输入框或 `link` → 抓正文（readability）→ 归一化 → 模型抽取 → 校验 → 生成 `Event/Task`（`state=candidate`）+ Claims → 收件箱。
失败态：链接抓不到 → 保留 URL，提示"粘贴正文"。

### 5.2 截图

上传 / 粘贴（`paste` 事件读剪贴板图片）→ 原图存 `storage/`（本地，不入库不入 git）→ 视觉模型直读，返回 `{ text, layout_hints, extraction }` → 后续同 5.1。
额外处理：
- 抽出聊天中可见的日期/发送人，作为 `messageDate` 锚点（读不出就 `needs_anchor`）。
- 原文展示时用 OCR 文本高亮，原图作为附件预览。

### 5.3 官网抓取 + 变更检测

`WatchTarget` → Job → Playwright 打开栏目页 → 取文章列表（选择器 + 兜底：找 `<a>` 中标题相似项）→ 新文章入库。
**变更检测复用 Claim 校验**：对已有 Source 重新抓取正文，逐条 Claim 检查 `source.text.includes(quote)`：
- 片段仍在 → 无变化（顺带刷新 `quoteStart`）
- 片段消失 → 该 Claim 置 `stale` → 对新正文跑一次抽取 → 同字段有不同值则生成 `Change`（待用户确认）

这样"官网改了截止时间"不需要单独的 diff 算法，是 `quote` 机制的副产品。

### 5.4 邮件

v0：拖入 `.eml` / `.mbox` → `mailparser` 解出 `subject/from/date/text/html/attachments` → 附件 PDF 用 `pdf-parse` 抽文字、图片走 5.2 → 抽取。
v1（可选）：`imapflow` 只读连接，按 `SINCE`/`SUBJECT` 拉取，**只存解析结果与原邮件引用（messageId），不存账号密码**。
诚实标注：v0 的 UI 文案必须是"导入邮件"，不得写"自动检索邮箱"。这条写进验收用例。

### 5.5 联网核实

```
query = `${profile.school} ${profile.college ?? ''} ${event.title} ${意图词} site:${schoolDomain}`
意图词 ∈ {通知, 报名, 材料, 截止, 实施 办法}
```

1. 搜索拿 3–5 条候选 → 抓正文 → 用**同一个抽取器**抽字段。
2. 逐字段比对：找到候选值且 quote 校验通过 → 新 Claim（`status=supported`，`origin=rule`），并在 UI 显示"官网支持/与现有值冲突"。
3. 适用性复核：模型输入 `{ profile, 事件, 候选来源 }`，输出 `{ applies: yes|no|unknown, reason, evidence_quote }`。`unknown` → 信息不足。
4. **身份线索不足时先问**（学校/学院/年级），不默认采用第一条结果。

耗时预期 8–20s：前端先显示"正在核实…（已找到 3 条候选）"的流式状态，可离开页面。

## 6. 合并：先守卫，再模型，最后用户

```ts
function mergeGuard(a: Event, b: Event): { score: number; reasons: string[] } {
  const termA = termKey(a), termB = termKey(b)   // 2026春 / 第3届 / 2026级
  if (termA && termB && termA !== termB) return { score: 0, reasons: ['届次/学期不同'] }

  let score = 0
  if (titleSimilarity(a.title, b.title) >= 0.6) score++
  if (a.org && a.org === b.org) score++
  if (a.startAt && b.startAt && daysBetween(a.startAt, b.startAt) <= 3) score++
  if (sameSourceFamily(a, b)) score++          // 同域名 / 同一邮件线程
  return { score, reasons: [...] }
}
```

`score >= 2` 才进入候选，再由模型判断"是否同一件事、差异字段有哪些"，输出理由。**原型阶段一律不自动合并**，`MergeCandidate` 出现在收件箱，用户点「合并 / 不是同一件事」。
合并实现：`Event.mergedIntoId` + 字段级 Claim 改指向（不复制值），因此**可撤销**——撤销即清空 `mergedIntoId`，原事件与 Claim 全在。
显式反例测试：同名不同届次 → `score=0`；同名同日不同学院 → 不合并。

## 7. 页面与关键组件

| 路由 | 内容 | 这一页要证明什么 |
|---|---|---|
| `/` 行动台 | 近 7 天截止（按 `Task.dueAt`）、重要变更、待确认项、今日日程 | 首页围绕"要做的事"，不按来源分栏 |
| `/inbox` 收件箱 | 候选事件/任务/合并建议/冲突，按来源徽标分组 | 多入口汇到同一处 |
| `/capture` 快捷收录 | 粘贴区、拖拽上传、链接、文本框；"联网核实"开关 | 四种入口一个交互 |
| `/events/[id]` 事件详情 | 时间线、任务清单（勾选）、材料、规则、字段出处、冲突面板、变更历史 | **每个字段点开都能看到原文与链接** |
| `/settings/sources` | 官网栏目、邮件导入记录、关注范围、隐私说明 | 能力边界说清楚（导入 ≠ 接入） |

关键组件：

- `<FieldValue field="dueAt">` — 值 + 状态点（支持/冲突/待确认）+ 点击弹出 `<SourcePopover>`（原文高亮、链接、发布与获取时间、确认按钮）。
- `<ConflictPanel>` — 并排候选值，各自出处，用户选一个（生成 `user_confirmed` Claim），**不提供"全部采用"**。
- `<ChangeList>` — 原值 → 新值，触发来源，确认/拒绝，可撤销。
- `<AnchorPrompt>` — "这条消息发于哪一天？"（仅当锚点缺失时出现）。
- `<MergeDialog>` — 并列两张卡，标出相同字段与不同字段。

## 10. 验收 → 自动化用例

策划文档 §12 的每一条，都对应一个 fixture 测试（`fixtures/acceptance/*`，纯 JSON + 期望输出，不依赖模型在线）。

| 验收条目 | 用例 | 断言 |
|---|---|---|
| 活动时间与报名截止不混 | `event-vs-deadline` | `event.startAt` 与 `task.dueAt` 分别存在且不等 |
| 缺锚点的"明天"待确认 | `relative-date-no-anchor` | `claim.status='needs_anchor'`，`value=null` |
| 新闻不变成待参加事件 | `news-not-actionable` | `actionable=false`，不进收件箱候选 |
| 同事件可提合并、不同届次不合并 | `merge-guard` | score ≥2 / score=0 两组 |
| 时间地点材料各有来源 | `field-provenance` | 三个字段的 claim.sourceId 各不相同 |
| 冲突可见不静默覆盖 | `conflict-no-overwrite` | 两条 supported 并存，`event` 视图标记 conflict |
| 无依据的扣分不编造 | `high-impact-gate` | `rule.state='unconfirmed'`，UI 文案含"未确认" |
| 用户可改/拒/撤/删 | `user-override` | 写 Claim(origin=user)，merge 撤销后原事件恢复 |
| 实现范围说明清楚 | `labeling` | 导入路径页面文案不含"自动检索邮箱" |

运行：`npm test`（Vitest，离线，跑 fixtures）。这条链路同时是**现场答辩的加分项**：评委给一条新通知，贴进去看断言是否成立。

另加两条工程测试：`claims: 不存在无来源的事件字段`（遍历 DB 断言）、`merge: 幂等`。

## 14. 隐私与安全落地清单

- `storage/` 与原邮件不入 git；`.env*` 不入 git；仓库内无任何真实凭证。
- 设置页列出"哪些内容会发往外部"：截图 → 视觉模型；正文 → 文本模型；核实查询 → 搜索服务。逐项可关。
- 上传截图时提示"图片可能包含他人姓名/头像，建议裁剪"，提供一键删除原图。
- 外部网页/邮件/截图里的文字一律视为数据，**不进系统提示、不触发工具调用**（抽取器只返回 JSON，没有工具权限）。
- 第一版不自动发邮件、不代报名、不代提交。

## 附录 A：为什么不用向量库

原型的数据量是"几十到几百条通知"。合并候选用确定性特征（标题 trigram + 组织 + 时间邻近 + 同源域）召回，召回率足够且**可解释**——评委问"为什么合并这两条"时，能指着四条理由回答。向量检索留到有上千条历史数据、需要"找相似往年通知"时再上。

## 附录 B：为什么不用 tRPC / 微服务 / Redis

原型的最优解是"一个进程能跑起来"。Server 层直接是函数调用，API 只为前端异步与文件上传存在；任务队列用一张表，几十条记录轮询毫无压力。技术复杂度留给真正难的部分：**证据模型**。
