## 2. 影响观感的 5 个主要问题

### 2.1 收录等待太长，进度页几乎是静止的（最影响节奏）

- 通知收录 **29.3 秒**，群聊收录 **48.6 秒**。
- 四步进度只点亮两次，中间没有时间感；画面大面积留白。105 秒片里如果原速放，会直接死掉。

**处理**：
- 105 秒：通知段 8× 加速（约 3.7 秒），群聊段 16× 加速（约 3.0 秒），角落标「实际耗时约 30 秒 / 49 秒」。
- 4 分钟：保留 3–5 秒真实进度，然后切到收件箱；旁白说明“真实模型约 30–50 秒”。
- 如果 App 侧愿意改：在进度页加一个已用时/预计剩余时间，或让步骤条有连续的细进度动画。这个改动对观感收益最大。

### 2.2 标题冲突是噪音，主叙事只需要地点冲突

- 群聊被抽成标题「讲座」，与官方长标题形成冲突；行动台因此显示 **2 处冲突**。
- 合并 diff 第一行变成「事件：公开讲座… → 讲座」，看起来像系统把正式标题改坏了。
- 适用对象也曾被抽成「2024级」，这次已收敛，但同类噪音还会出现。

**处理（必须）**：
- 开录前在事件详情里对「讲座」这条标题 claim 点「拒绝」，只保留地点冲突；目标 `conflict_count = 1`。
- 如果装载 Agent 能直接准备干净状态，优先用干净状态；不要在片子里解释“为什么标题变了”。
- 合并 diff 只保留地点与新增待办/材料，不要出现标题变更。

### 2.3 合并 diff 没显示材料新增

- 实际 diff 只有三行：事件（标题变化）、地点（思源 → 劳伦斯）、新增待办（无 → 报名）。
- 「one-page project intro」只出现在候选摘要和合并后的任务里，**不在 diff 表**。
- 用户的分镜预期是“diff（地点；新增待办与材料）”，当前画面撑不住“材料”这半句。

**处理（二选一）**：
- App 侧把 task materials 纳入 `Merge.diff`，或至少把材料变化列成一行。
- 或者改分镜：先拍候选摘要里的“随报名表提交一份 one-page project intro”，再拍合并后的任务 chips；不要把“材料”归因给 diff 表。

### 2.4 导出 `.ics` 没有可见的成功反馈，且结束时间多了 30 分钟

- 下载事件真实发生，文件保存为 `recordings/_trial/downloads/ontime-61d54b.ics`。
- 但页面没有任何 toast；无头浏览器也没有下载架，画面里等于“点了一下，什么也没发生”。
- **另外，导出的 ICS 结束时间不对**：`DTSTART:20261115T013000Z`（09:30）、`DTEND:20261115T033000Z`（11:30），而事件详情是 09:30–11:00。日历里凭空多了 30 分钟。

**处理（必须）**：
- 优先让 App 在点击后显示「已导出日历」的轻提示；这是最稳的。
- 或者用有头 Chrome + 下载架录制，画面里出现 `.ics` 下载项。
- 修 ICS 生成：`DTEND` 应为 `20261115T030000Z`（11:00），不要用默认 2 小时。
- 不要后期 P 一个假提示；最多用真实文件名做角标，但要有真实下载文件对应。

### 2.5 行动台勾选后计数不一致

- 勾掉「完成注册」后，「近 7 天要做的事」显示 **0 件未完成**。
- 但「已确认事件」那一行仍然显示 **2 件待办**（`open_task_count` 没有随勾选刷新）。
- 同一屏出现两个互相矛盾的数字，评委很容易注意到。

**处理（必须）**：
- App 侧在 `toggleTask` 后刷新 event 的 `open_task_count`（或前端本地同步）。
- 或者在片子里避免同屏出现这两个数字：勾选后切走，不拍事件行的徽标。但这是掩盖，不如修。

## 3. 另外 3 个次要问题

### 3.1 `this Friday` 没有成为字段的 quote

- 「报名」任务的截止状态是 **待确认**，这是对的（见 `04b-task-pending.mp4`）。
- 但它的原文 quote 是「报名要在12号前完成哈」，不是群里那句 `deadline 是 12 号还是 this Friday?`。
- 右侧来源面板的群聊缩略文里能看到 `this Friday`，但字段气泡里没有；1440×900 下这两个信息不在同一屏。

**处理**：
- 如果一定要拍“`this Friday` → 待确认”，需要抽取器把这句话作为 due_at 的 quote；或者固定用两个镜头：先拍字段「待确认」，再拍右侧群聊原文里的 `this Friday`，中间用后期 callout 连接。
- 不要把 `this Friday` 换算成具体日期；这一点当前是对的。

### 3.2 群聊来的材料显示绿色「已支持」，容易被读成“官方支持”

- 「报名」任务的「所需材料 one-page project intro、报名表」状态是 **已支持**（绿色）。
- 点开出处能看到 quote 和 `unnc_chat.png`，但主行没有“来源=群聊、非官方通知”的提示。
- 观众的直觉会把绿色读成“官方认可”，与“没有官方依据”的叙事冲突。

**处理**：
- 105 秒里给材料一个特写：绿色状态点旁边补后期小字「来源：群聊」；或拍字段展开后的来源缩略图。
- App 侧更彻底的做法：字段状态区分「官方来源支持」与「用户来源支持」，不要都用同一个绿色。

### 3.3 匹配分 1.5 / 5 看起来像“系统也不确定”

- 合并卡显示「匹配分 1.5 / 5」，但理由行其实很有说服力（同一场 15 号上午 9:30，地点变更，补充报名与材料）。
- 观众会把 1.5/5 读成“置信度 30%”，与“建议合并”矛盾。

**处理**：
- 105 秒里裁掉分数，只保留理由行；或加一行小字「匹配分是规则得分，不是概率」。
- 不要把分数后期改成高分。

### 3.4 收件箱同时出现候选卡和合并建议，画面偏挤

- 候选卡「讲座」带 3 条 questions，占了大半屏；合并建议在下方。
- 105 秒里建议直接裁到合并建议卡（从「合并建议」标题开始），不要展示候选卡的提问。
- 4 分钟里可以保留，但旁白要明确“这是同一件事的两条线索”。
